XML → JSON 変換 FAQ

XML、JSON 形式変換、API データ交換、Web Services に関するよくある質問です。

XML（Extensible Markup Language）と JSON（JavaScript Object Notation）はどちらも構造化データ形式ですが、設計思想には大きな違いがあります。

機能 XML JSON
可読性 中程度 — タグが多い 優秀 - シンプルで軽量
対応タイプ plain text では type がないため、Schema で定義する必要があります。 string、number、Boolean、Null、array、object をネイティブに扱えます。
メタデータ ✅ 組み込み Attribute 機構 ❌ ネイティブ Attribute がありません
Namespace ✅ xmlns に対応 ❌ 非対応
注釈 ✅ <!-- --> ❌ 非対応
解析速度 低速（タグ構造の解析が必要） 非常に高速（ネイティブ JavaScript 対応）
ファイルサイズ より大きい（開始／終了タグが重複） 小さめ（記号数が最少）

形式選択の目安：複雑なファイル構造、Namespace、Attribute を使ったデータ受け渡しが必要なら XML、Web API やフロントエンド／バックエンド間通信、軽量なデータ交換なら JSON が向いています。現在の API の多くは XML を受け取っても、内部では JSON へ変換して処理します。

SOAPSOAP（Simple Object Access Protocol）は、Microsoft が 1998 年に提案した XML ベースの厳密な通信プロトコルです。SOAP message は XML 形式を使用し、Envelope → Header → Body という厳格な構造に従う必要があります。

RESTREST（Representational State Transfer）は、Roy Fielding が 2000 年に提唱した軽量な API 設計スタイルです。REST API では一般に JSON が使われますが、XML 形式にも対応できます。

SOAP の特徴

  • 厳密な WSDL 定義
  • 組み込みセキュリティ仕様（WS-Security）
  • stateful または stateless
  • XML 形式のみ対応
  • エンタープライズ向けアプリケーション、金融システム

REST の特徴

  • リソース指向設計（URI）
  • ステートレス
  • JSON / XML / プレーンテキストに対応
  • 標準 HTTP method（GET / POST / PUT / DELETE）を使用します。
  • モダンな Web・モバイルアプリケーション

modernization の過程では、多くの企業が SOAP/XML の Legacy API を REST/JSON architecture へ移行します。このツールは、そうした変換シナリオ向けに設計されています。

Sitemap XMLSitemap は、サイト内にどのページが存在するか、どの程度の頻度で更新されるか、相対的な重要度などを検索エンジンへ伝える XML ファイルです。標準形式は sitemaps.org で定義されています。

<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://example.com/</loc>
    <lastmod>2024-01-15</lastmod>
    <changefreq>daily</changefreq>
    <priority>1.0</priority>
  </url>
</urlset>

Sitemap XML が SEO に重要な理由は次のとおりです。

  • 検索エンジンが新規ページや更新コンテンツをより早く発見できるようにします。
  • 大規模サイトのすべてのページがインデックスされるようにします
  • relay information（最終更新時刻、変更頻度）を提供します。
  • image、video、news など特殊な content type に対応します。

RSSRSS（Really Simple Syndication）は、blog、news、podcast など頻繁に更新されるコンテンツを配信する XML ベースの購読形式です。RSS feed は本質的には XML ファイルです。

<?xml version="1.0" encoding="UTF-8"?> <rss version="2.0"> <channel> <title>ToolHub Blog</title> <link>https://toolhub.example.com/</link> <item> <title>JSON vs XML Comprehensive Comparison</title> <pubDate>Mon, 15 Jan 2024 10:00:00 GMT</pubDate> </item> </channel> </rss>

RSS フィードの主な用途:

  • ユーザーがブログやニュースサイトの最新コンテンツを購読できるようにします。
  • Podcast 配信・公開。Apple Podcasts、Spotify などのプラットフォームは RSS を利用します。
  • コンテンツ集約と自動ワークフロー
  • social media scheduling と content republishing に利用できます。

XML を JSON へ変換するとき、Attribute と Text node の扱いは最も重要な設計判断の一つです。このツールでは 3 つの option を用意しています。

  • @ プレフィックス（有効化推奨）： XML Attribute を次へ変更 @ プレフィックスの key 表現。例： <book category="fiction"> → "@category": "fiction"。この方法なら attribute と child element を明確に区別できます。
  • #text node: 要素に Attribute とテキスト内容の両方がある場合、テキスト内容は次の位置に配置されます #text キー。例: <title lang="en">Hello</title> → {"@lang": "en", "#text": "Hello"}。
  • 予約属性： この option を無効にすると、すべての attribute を無視し、element の内容だけを保持します。テキスト内容だけが必要な場面に適しています。

例：

XML: <book id="b1" lang="en">The Hobbit</book> ✅ @prefix + #text: {"@id": "b1", "@lang": "en", "#text": "The Hobbit"} ❌ None Attribute: "The Hobbit"

100% 安全です。 このツールは純フロントエンド（Client-side）構成で、XML の解析と JSON への変換はすべてブラウザー内で完結します。データがサーバーへアップロードされることはありません。

つまり：

  • API specification、sitemap data、RSS feed configuration が端末外へ送信されることはありません。
  • 変換処理そのものに internet connection は不要です。初回の page load 時を除き、offline でも実行できます。
  • バックエンドサーバーが内容を保存・処理することはありません
  • 入力したデータには ToolHub の管理者でさえアクセスできません

SOAP API の XML request、Sitemap 設定、Legacy system データなども、ここで安全に処理できます。

XML を JSON へ変換すると、2 つの形式の構造上の違いにより、変換結果の調整が必要になる場合があります。以下は一般的な構造変化と処理方法です。

  • 繰り返し element は自動的に array へ変換されます。 XML 内で同じ名前の child element が繰り返される場合（例：複数の <item>）は JSON 配列に変換されます。
  • 属性が単独の属性として存在します： @ prefix を有効にすると Attribute が独立した JSON Key となり、child element と混同しなくなります。
  • 空要素の処理： 空の XML 要素（<element></element>) は、設定によって Null または空文字列へ変換される場合があります。
  • Mixed content： element に text と child element の両方が含まれる場合、text は次のように配置されます。 #text キー。

推奨：変換後は JSON 構造を元の XML と照合し、特に配列とネストしたオブジェクトが正しいか確認してください。Tree View モードを使うと JSON 構造を直感的に確認できます。

XML から JSON へ：現代 Web development における data format の進化と実践ガイド

25 年を超える Web technology の発展の中で、XML（eXtensible Markup Language）を使って JSON（JavaScript Object Notation）は、それぞれ異なる時代を代表するデータ交換標準です。XML が 1998 年に W3C 推奨仕様となり、2010 年代には JSON が Web API の事実上の標準へ発展しました。両者の変換を理解することは技術要件にとどまらず、Web アーキテクチャの進化を理解するうえでも重要な視点になります。

XML とは何ですか？

XML（Extensible Markup Language）は 1998 年に W3C によって策定されたExtensible Markup Language、設計目標は「人が読め、機械でも解析できる」ことです。XML はカスタムタグ（Tags）でデータ構造を記述し、次の機能をサポートします Attribute、Namespace、Schema（XSD） その他の豊富な機能。

XML の設計思想は"厳密かつ完全". 各 XML file には root element が必要で、すべての tag を正しく閉じ、attribute value は quote で囲む必要があります。この厳密さにより、enterprise application、financial system、medical record、legal document など、高度な構造化と検証が必要な場面があります。主な用途には次のようなものがあります。

  • SOAP Web サービス — エンタープライズ向け API 通信プロトコルで、XML 形式に厳密に依存します
  • Sitemap XML — 検索エンジン向け Sitemap の標準形式
  • RSS / Atom Feed — コンテンツ購読・配信形式
  • SVG — スケーラブルベクターグラフィックス（XML ベース）
  • Docx / Xlsx — Microsoft Office ファイル形式（内部で XML を使用）
  • XHTML — 厳格な HTML バージョン
  • 設定ファイル — Maven POM、Ant Build、Spring XML など

JSON とは何ですか？

JSON（JavaScript Object Notation）は Douglas Crockford により 2001 年に標準化され、軽量なデータ交換形式. JSON は JavaScript syntax の subset から派生しており、キーと値のペア 付き配列 簡潔な構文でデータを整理でき、非常に効率よく解析できます。

JSON の設計思想は"シンプルで効率的"。closing tag、attribute、namespace が不要というミニマルな設計により、JSON は Web 開発で急速に普及しました。主な利点は：

  • RESTful API — モダン Web API で推奨される形式
  • NoSQL データベース — MongoDB、CouchDB などは JSON-like な file storage を使います。
  • フロントエンド開発 — React、Vue、Angular などの framework は JSON を native に処理します。
  • Profile — package.json、tsconfig.json、.eslintrc.json など。
  • インスタントメッセージング — WebSocket メッセージ形式

XML → JSON の実用例

XML 入力

<?xml version="1.0" encoding="UTF-8"?>
<api-response>
  <status>success</status>
  <data>
    <user id="u001" role="admin">
      <name>John Doe</name>
      <email>john@example.com</email>
      <permissions>
        <permission>read</permission>
        <permission>write</permission>
        <permission>delete</permission>
      </permissions>
    </user>
  </data>
  <meta>
    <requestId>req-2024-001</requestId>
    <timestamp>2024-01-15T10:30:00Z</timestamp>
  </meta>
</api-response>

JSON 出力

{
  "api-response": {
    "status": "success",
    "data": {
      "user": {
        "@id": "u001",
        "@role": "admin",
        "name": "John Doe",
        "email": "john@example.com",
        "permissions": {
          "permission": [
            "read",
            "write",
            "delete"
          ]
        }
      }
    },
    "meta": {
      "requestId": "req-2024-001",
      "timestamp": "2024-01-15T10:30:00Z"
    }
  }
}

As you can see, Attribute (id, role) is reserved with @ prefix, and repeated <permission> elements are automatically merged into arrays.
